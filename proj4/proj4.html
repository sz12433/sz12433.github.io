Part 1: Fit a Neural Field to a 2D Image

Architecture Details:

  • Hidden Layers: 3 hidden linear layers
  • Width: 256, but tried both 32 and 256
  • Positional Encoding: 2D positional encoding with max frequency L (tried L=4 and L=10)
  • Input Dimension: 2 + 4*L (after positional encoding)
  • Output: 3 channels (RGB) with Sigmoid activation to output values in [0,1]
  • Activation: ReLU for hidden layers, Sigmoid for output

Training Hyperparameters:

  • Learning Rate: 1e-2 (0.01)
  • Optimizer: Adam
  • Batch Size: 10,000 pixels per iteration
  • Number of Iterations: 2,000
  • Loss Function: MSE (Mean Squared Error)
  • Evaluation Metric: PSNR (Peak Signal-to-Noise Ratio)

Essentially, the model uses positional encoding to map 2D pixel coordinates (x, y) to a higher-dimensional feature space with sinusoidal functions at different frequencies (2^0, 2^1, ..., 2^(L-1)). From there, the positional encoding produces features of dimension 2 + 4*L, which are then passed through the 3-layer MLP with ReLU activations for predicting RGB color values.

Part 2: Fit a Neural Radiance Field from Multi-view Images

Part 2.1: Create Rays from Cameras

To create rays from camera images, I first implemented 3 helper functions that were described in the spec to handle camera to world coordinate conversion, pixel to camera coordinate conversion, and pixel to ray conversion.

First, I created a transform(c2w, x_c) function to convert 3D points from camera coordinates to world coordinates using the camera-to-world transformation matrix. This process involved adding a homogeneous coordinate to the points, multiplying by the c2w matrix, and then de-homogenizing the result by dividing by the homogeneous coordinate.

Next, to implement pixel_to_camera(K, uv, s), I inverted the pinhole camera projection equations to convert 2D pixel coordinates back to 3D camera coordinates. This function basically extracts the intrinsic parameters from the camera matrix, and then applies the inverse projection formulas to find camera coordinates.

Then, to convert a pixel coordinate to a ray with origin and normalized direction, I defined the pixel_to_ray(K, c2w, uv) function to combine the previous two functions. This function computes the ray origin from the camera position in world coordinates, (using c2w), then uses pixel_to_camera to get a 3D point in camera space, transforms it to world coordinates using the transform helper function, and then calculates the normalized ray direction.

Part 2.2: Sampling

When it comes to sampling, I first implemented a sample_rays function that followed the spec's second strategy of flattening the pixels across all images and then doing a global random sample one time for ray sampling.

Then, to sample points along each ray, I created a sample_along_rays function that would essentially randomly sample from a uniform distribution between the near and far bounds for each ray. Within the bins, I also followed the spec's formula of adding a random fraction of the bin's width to avoid training the model on a fixed set of points, and ensure that every location along the ray may be sampled.

Part 2.3: Putting the Dataloading All Together

In this next part, I first implemented a new RaysData class to then use the provided visualization code to verify cameras and rays to check if everything looks reasonable. After randomly sampling rays from images, RaysData then uses the pixel_to_ray function to convert pixel coordinates to rays, and stores the ray origins, directions, and corresponding RGB colors for training.

After that, I used the provided visualization code to visualize the camera positions and ray directions in Visers. I believe the cameras are represented as frustums in 3D space, and the rays are shown as lines originating from the camera centers. This visualization helped confirm that the rays were correctly generated from the camera parameters and that they were pointing in the right directions. (Image is shown below!)

Part 2.4: Neural Radiance Field

To prepare for working in 3D space, I updated my PositionalEncoder class to a new 3D version that could handle 3D coordinates instead of 2D. This involved modifying the original implementation to take 3D input points and apply sinusoidal functions across all three dimensions (x, y, z), and then concatenating the original coordinates with the encoded features.

Next, I created a new NeRF class to build the deep MLP as described in the spec. Based on the provided diagram, the NeRF consists of 8 layers for the MLP, with ReLU activations at each hidden layer. There's also a linear layer injected after the 4th layer that receives features from the previous layer as well as the original position vector. After a final color layer, a Sigmoid activation is applied to ensure the RGB outputs are in the range [0, 1].

Part 2.5: Volume Rendering

First, I implemented the volume rendering equation for a batch of samples along a ray in the vol_rend function. The vol_rend function first calculated transmittance from subtracting an alpha value from 1, which was also computed by taking the product of the densities and distances between samples (sigma and delta), by following the formula provided in the spec. From there, we can build a list of weights for each sample along the ray by multiplying the transmittance with the alpha values, and then use torch.cumprod to compute the cumulative product needed for transmittance. I then checked the functionality by running the provided assert statement!

To train the NeRF model on the lego dataset, I combined the 3 helper functions from part 2.1 along with the dataloader RaysData from 2.3 to sample rays and points along those rays. For each batch of rays, I used the NeRF model to predict colors and densities at the sampled points, and then applied the volume rendering function from 2.5 to compute the final pixel colors. The loss was calculated as the MSE between the rendered colors and the ground truth pixel colors.

In terms of my model architecture, see the below lists with details!

Architecture Details:

  • Depth: 8 connected layers
  • Width: 256
  • Positional Encoding: uses L = 10 frequencies for x, y, and z
  • Input Dimension: position encoding = 63, direction encoding = 27
  • Output: density, color (RGB)
  • Activation: ReLU for hidden layers and for density, Sigmoid for RGB

Training Hyperparameters:

  • Learning Rate: 5e-4 (0.0005)
  • Optimizer: Adam
  • Batch Size: 4096 rays sper step
  • Number of Iterations: 1500
  • Number of Samples: 64 (per ray)
  • Near: 2.0
  • Far: 6.0
  • Loss Function: MSE (Mean Squared Error)
  • Evaluation Metric: PSNR (Peak Signal-to-Noise Ratio)

To elaborate on the training parameters in particular, I changed some of my hyperparameters to be different than those listed in the spec to try and save some computation time. For example, instead of 10,000 rays per gradient step, I used 4,096, and instead of 1000 gradient steps, I iterated over 1500. However, since I added a conditional statement that would break out of the training loop if we hit 23 validation psnr, my training actually termminated in 1250 iterations out of the original 1500. The main reason I decreased the batch size by more than half is because I actually had implemented everything at this point in my local VSCode environment on a M1 mac mps backend. However, this took a long time for me to run, especially when I was taking 10,000 rays per gradient step, so I switched to 4096. Even then, it would still take around 40 minutes to finish training and reach a 23 validation, which made some of my experimentation difficult. As a result, after receiving advice from OH, I transferred my code to Colab to use the T4 GPU for part 2.6!

Part 2.6: Training with Your Own Data

Architecture Details:

  • Depth: 8 connected layers
  • Width: 256
  • Positional Encoding: uses L = 8 frequencies for x, y, and z
  • Input Dimension: position encoding = 63, direction encoding = 27
  • Output: density, color (RGB)
  • Activation: ReLU for hidden layers and for density, Sigmoid for RGB

Training Hyperparameters:

  • Learning Rate: 5e-4 (0.0005)
  • Optimizer: Adam
  • Batch Size: 10000 rays sper step
  • Number of Iterations: 2000
  • Number of Samples: 64 (per ray)
  • Near: 0.01
  • Far: 0.8
  • Loss Function: MSE (Mean Squared Error)
  • Evaluation Metric: PSNR (Peak Signal-to-Noise Ratio)

Moving from my VSCode to the Colab notebook environment, I now increased my batch size back up to 10,000 rays to try and capture more information per gradient step now that I could run on a stronger GPU that could compute faster than before. Additionally, although I kept the same learning rate as for the lego data, I actually added in a decay for the learning rate using the CosineAnnealingLR so that the learning rate would gradually decrease over time by following the curve of a cosine function. I added this because I noticed that although my training PSNR would rapidly increase, my validation PSNR would actually start to decrease, which seemed to indicate to me that my model was beginning to overfitt. As a result, this learning rate decay helped my validation PSNR from dropping as rapidly, and seemed to be more stabilized than before.

I also decreased my L positional encoding parameter from 10 to 8, because I found that with 10 frequencies, my model seemed to overfit more quickly to the training data, leading to artifacts in the rendered images. Regarding other hyperparameters, after some experimentation and also some physical measurement of where I took my photo (I did look funny trying to measure the distance from my camera to my original Octo plushie) I adjusted my near and far bounds to = 0.01 and 0.8 respectively based on the idea that these distances may somewhat represent the meters from the camera.

To briefly comment on my generated gif, I actually went through a lot of trial and error because I think I did some rotations incorrectly initially (see below for some silly attempts -- not sure why some of my orbits rotated the camera through the table??) before I finally got a clean orbit around my octo plushie. At these points behind my object, it seems like the aruco tags would almost disappear and it became much harder to distinguish the object and the tag. However, it was really cool to see what views the model could come up with to simulate the camera rotation around my plushie, especially since they cana be believable to even the human eye!
